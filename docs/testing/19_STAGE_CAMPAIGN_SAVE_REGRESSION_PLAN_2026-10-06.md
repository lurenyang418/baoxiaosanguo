# 19 关连续通关与存档回归测试计划（2026-10-06）

截至 2026-10-13 的验收摘要见[当前回归状态](REGRESSION_STATUS.md)。

## 目标

验证当前 Godot 原型能否从标题画面开始，按正常游戏操作连续完成第 1 至第 19 关，并验证战斗存档、队伍成长、选将、失败重试和通关记录在跨关及重启后保持一致。

本计划验证当前实现的稳定性，不把测试结果解释为已经达到 100% 原版复刻。原版 AI 分支、特殊关胜利条件等仍有近似实现；发现差异时要记录为实现缺陷或已知保真度限制，不能为了让测试通过而注入胜利状态。

## 测试保护规则

- 所有自动化和手动流程使用独立的测试存档名或独立 Godot 用户数据目录。开始前记录现有正式存档是否存在及其 SHA-256；结束后再次核对。
- 不覆盖、移动或删除用户现有存档、构建包和研究文件。测试生成的存档、录像、日志和截图留在独立的测试输出目录，并在执行报告中记录其位置。
- 连续通关必须通过正常操作移动、攻击、使用当前可用技能、结束回合并触发游戏判定。允许 A 快进已有的回合播放；不允许直接改血量、设置 `demo_clear`、跳关或伪造关卡结果。
- 可用自动化构造边界存档验证拒绝逻辑；这些构造测试必须与“自然通关”记录分开。
- 每轮测试记录 Godot 版本、源代码提交/工作树差异、构建包哈希、设备/系统、操作步骤和最终结果。

## 第一阶段：搭建隔离测试环境

1. 核实当前项目导入成功，能从标题启动第一关；记录 Godot 版本、目标平台和起始源码状态。
2. 为自动化探针提供单独的存档路径（例如启动后将 `DemoSave.save_path` 指向 `user://campaign_regression_save.json`），不要使用默认的 `bao_xiao_san_guo_demo_progress.json`。验证探针读写的确是隔离文件。
3. 手动通关使用独立 Debug 配置或明确切换到同一隔离存档。若不能保证隔离，就先停止真实游戏流程，完成存档路径隔离后再开始。
4. 从 ROM 派生数据整理 19 关基准表：关卡索引、场景路径、地图尺寸、双方部署数、特殊胜利条件、失败条件；第 11–19 关另记录选将上限 `8/6/8/8/10/10/10/10/12`。未知或近似项明确标注，不自行猜测。

**通过条件：**正式存档哈希前后不变；隔离存档能独立写入、读取和清空测试状态（测试目录保留用于审阅）。

## 第二阶段：存档往返自动回归

以临时 Godot 场景/脚本探针运行，不替代实际操作验收。每种状态先保存快照 A，再重载游戏或场景，读取快照 B，逐字段比较：

- 当前关卡、我方与敌方队伍顺序、兵种、经验、HP、坐标。
- 己方已行动单位、回合数、光标、垂直滚屏位置及 ROM 敌军滚屏位置。
- 第 11–19 关的选将名单及顺序；成长或转职后的队伍数据。
- 通关状态与 20 人队伍的兵种、经验记录。

覆盖检查点：

1. 第一关初始状态、己方部分单位行动后、结束一回合后。
2. 垂直滚屏发生后，以及存读档发生在单位受伤或击败敌人之后。
3. 一次经验增长或升级/转职选择之后；确认新移动力和兵种在重载及下一关继续生效。
4. 第 11 关选将确认后保存；读取后名单、人数上限、队伍顺序一致。
5. 中后期（建议第 15 关）读档跨场景恢复；最后一关胜利并进入结局后保存通关记录，再从标题读取。

另测异常文件：无文件、非法 JSON、未知版本、错误关卡、数组长度不匹配、越界坐标、非法 HP/经验、重复选将、不可达转职和损坏通关记录。预期为给出可理解的失败提示，不崩溃、不把非法数据应用到战斗中，并保留正式存档。

**通过条件：**每个有效快照往返后字段完全一致；非法快照被拒绝且游戏仍可继续；加载通关记录进入记录页而不重开第 19 关。

## 第三阶段：19 关连续自然通关

由玩家从标题进入第一关，不读入预设胜利存档，不重置关卡状态。每关按顺序完成并记录：

1. 关卡和地图加载正确；我方、敌方、友军部署与基准表一致。
2. 逐个确认正常指令可用；移动范围使用当前兵种移动力，行动次数和回合切换正常。
3. 敌方/自动友军阶段能开始、完成并返回我方；快进不重复结算伤害、经验或回合。
4. 依游戏当前判定取得胜利；胜利面板只在自动回合播放结束后显示。
5. 按 A 进入下一关。第 11–19 关验证选将名单有效、人数不超过该关上限、已成长队员数据保留。
6. 在第 1、5、10、11、15、18、19 关额外做一次存档重启回归。每次记录存档哈希、恢复后的关卡与队伍字段。
7. 最终确认胜利庆祝动画、动画跳过、通关记录、保存记录、回标题及从标题读回记录。

**关卡记录表：**每关一行，记录开始截图、部署核验、胜利条件、用时/回合数、异常、是否读档、读档前后状态摘要、结束截图及通过/失败。阶段失败后保留日志并停止跳关；修复后从失败关及其前一关复测，之后再完成一轮连续流程。

**通过条件：**同一次自然游玩记录覆盖第 1–19 关；关卡严格连续；每关依当前胜利判定过关；全程无崩溃、软锁、丢失队伍成长、错误选将或重复结算；第 19 关到结局记录的存取流程正确。

## 第四阶段：失败、重试与进度边界

在隔离存档中额外进行一次可控失败流程：触发己方失败判定，选择重试；确认回到当前关起始状态，上一关已提交的队伍成长不丢失，失败关未错误地写入胜利进度。随后另测返回标题并读取最近一次合法战斗存档。

检查胜利提交边界：胜利后继续下一关才提交跨关成长；中途退出/重启不会出现队伍经验已加、关卡却回退或重复加经验。最后一关通关记录保存是显式操作，应确认保存之前不静默覆盖旧测试档。

## 第五阶段：打包版本冒烟检查

只在桌面自然通关和存档回归稳定后执行，避免把多平台差异混入基础定位：

- Apple Silicon macOS Debug App：启动、输入、音乐、隔离存档读写和至少一次跨场景加载。
- Android ARM64：安装当前 APK，横屏、触屏移动/确认、音频、前后台切换后的存档恢复。
- Windows x64：在 Windows 设备或虚拟机启动当前 EXE，确认资源、声音、键盘/手柄输入和存档目录可写。
- iOS：目前只有 Xcode 工程；须安装 Xcode iOS 平台组件、设置真实 Team ID/Bundle ID 并签名后，才能列入设备测试。此阶段不将未签名工程算作 iOS 通过。

## 交付记录

将测试日志、19 关表格、存档字段比较结果、正式存档前后哈希和截图保存在独立的测试输出目录。最终摘要中分开列出：自然通关结果、存档回归结果、平台冒烟结果、发现并修复的问题、仍存在的原版差异。测试未跑完时标注已覆盖的关卡和阻塞点，不用“全流程通过”概括部分检查。需要随项目共享的结论整理到 `docs/testing/REGRESSION_STATUS.md`，避免长期文档依赖本机路径。

## 建议执行顺序

先完成存档隔离和边界自动回归，再从第一关进行一次连续自然通关；一旦发现阻断性问题就记录、修复并重跑相关回归。自然通关稳定后再测失败重试和平台包。这样先保护真实存档并建立可复现的判定，再投入最长的 19 关手动流程。

```mermaid
flowchart LR
    ENV[隔离测试环境与存档] --> SAVE[存档往返与坏档边界]
    SAVE --> CAMPAIGN[第 1 至 19 关自然通关]
    CAMPAIGN --> RETRY[失败重试与进度提交边界]
    RETRY --> PLATFORM[桌面与移动平台冒烟]
```

遇到阻断问题时先记录并修复，再重跑失败阶段及其前置关；平台冒烟安排在桌面全流程和存档回归稳定之后。
